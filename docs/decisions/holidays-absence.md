> BCC Holidays & Absence: People sub-sections being built now, decisions + data model

Holidays & Absence = two sub-sections nested UNDER People in the sidebar. Phil chose **"start now"** (NOT Additions), 2026-07-11. Built as an extension of Phase 3 People, reusing its patterns. Full spec in PHASES.md ("People extension — Holidays & Absence").

**PERMANENT 2026-07-26: there is NO Holiday Response form.** Phil: "in forms - holidays - delete - holiday respone fpr all companies and founder". Migration 0129 deleted it from every company AND from the founder template library (it held no Evidence; a copy holding Evidence would be archived instead, since evidence.form_id is ON DELETE RESTRICT). Approving or declining a holiday is a DECISION, not a form: the Holiday screen shows **Approve** (one click) and **Decline** (reveals a required reason), both through the shared ActionForm. decideHoliday takes `decision` + `decline_reason` from the form data, submits NO Evidence, and calls decide_holiday_request with a null evidence id; outcome, decider, timestamp and reason live on the holiday_requests row, and the requester is still emailed. NEVER reintroduce a form for the yes or no.

Decisions (Phil popups 2026-07-11):
- Nav: "Holiday" and "Absence" are CHILD links under the People nav item (extend lib/nav NavEntry with children[], render expandable group in app-nav + mobile dock). People itself = existing register.
- ABSENCE view (/people/absence): branch cards for ONLY people with absences recorded, each showing current stage/action. Manager/Admin records absences against a Person (Absence Back Office form -> Evidence). Threshold crossed -> Absence Management Meeting recorded (Stage 1-4 -> Evidence).
- HOLIDAY view (/people/holiday): NOT cards. Top = pending-requests strip (approve/decline). Below = branch holiday calendar. NO balance/entitlement (approve/deny only). Requests now arrive mainly through the PUBLIC form link, see [public-forms-built](public-forms-built.md).
- Model = lifecycle/log, NOT recurring Check/RAG. Absence stage/score AUTO-DERIVED from recorded absences over a rolling window.
- Absence method = COMPANY SETTING, both supported: Settings > Absence, Admin picks Trigger points (Stage 1-4, occasions/days) or Bradford Factor (S^2 x D, action bands), sets thresholds, uploads policy (private storage, audit-logged). **AI (Anthropic) reads the policy and SUGGESTS method+thresholds** for Admin to confirm — Phil explicitly chose the AI route (satisfies ask-before-AI rule); meter AI usage per company.
- Evidence via the EXISTING founder forms (holiday_requests, absence_back_office, absence_management_meeting) through submit_evidence(record_type='person', record_id=person_id). No parallel pipeline; dedicated tables hold status/dates/stage.
- Permissions (RLS): TM submits + sees only OWN holiday/absence; Manager approves/declines + records absences for their branch(es); Supervisor = caseload; Admin/Platform = all.

Data model = migration 0041 (ref bgrtcvyjuwopunpnudeu ONLY + numbered SQL): absence_config, holiday_requests, absence_events, absence_meetings + person_absence_status view + SECURITY DEFINER RPCs + private policy bucket. RLS mirrors People helpers (is_branch_manager/is_person_supervisor/is_company_admin/requested_by=auth.uid()).

KNOWN DEPENDENCY: TM login is not linked to a Person record (people.profile_id dormant, manual link removed in Phase 3). So TM holiday requests key on requested_by=user (fine for the requests strip + branch calendar); per-person Holiday history in the Person drill-down only fills once a profile<->Person link exists. Public form submissions DO link to the Person (matched by personal email), so they land on the record properly. Absence is unaffected (Manager records directly against a Person).
