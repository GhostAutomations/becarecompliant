## Security

### S1. High: a Company Admin can make themselves Founder

- **Where:** `profiles_update` policy and trigger `enforce_profile_protected_fields`.
  - The policy lets anyone update their own row (`id = auth.uid()`).
  - The trigger lets a Company Admin change `role` and `company_id` on any row of their company, **their own included**.
  - The check constraint `platform_admin_has_no_company` only needs `company_id` to be null as well.
- **Proof (rolled back):** as Bevan's Company Admin (`ca13390c…`):
  - `update profiles set role='platform_admin', company_id=null where id = <self>` updated 1 row.
  - `is_platform_admin()` then returned true.
  - The same login then saw Thistle's 14 people, 12 Service Users and all 5 companies.
- **Why it matters:** anyone with Admin on any customer can read every customer's special category data. It takes one call from the browser console with their normal login. No server code is involved.
- **Likely fix:** in the trigger:
  - Nobody but the Founder may set `role = 'platform_admin'` or change `company_id`.
  - A Company Admin may change the role or status of other people in their own company only, never their own role, company or status.
  - Add an advisor style unit test that tries it.

### S2. High: a Company Admin can join any other company

- **Where:** the same policy and trigger as S1.
- **Proof (rolled back):** as Bevan's Company Admin:
  - `update profiles set company_id='<Thistle id>' where id = <self>` updated 1 row.
  - `is_company_admin(Thistle)` returned true.
  - The login could read Thistle's 12 Service Users and 71 Evidence rows.
- **Why it matters:** cross tenant takeover. It needs the target company's id, which is not secret forever (it appears in URLs, exports and links).
- **Likely fix:** the S1 fix closes it. `company_id` changes only by the Founder or by the invite acceptance code running as the service role.

### S3. High: Storage lets every company login read every stored Evidence file

- **Where:** Storage policy `evidence_objects_select` on bucket `evidence`: `is_platform_admin() OR is_company_member(<first folder>)`.
- **Proof (rolled back):** as a Thistle carer (`staff` role, `7d990f34…`):
  - `storage.objects` listed 5 Thistle objects: the logo, a policy PDF, and 3 `render/evidence.pdf` files.
  - The `evidence` table showed that carer none of those 3 Evidence rows.
  - One of the PDFs is a Service User Audit from 18 Sep.
- **What else sits in that bucket today:**
  - fit notes (RTW, health data)
  - paper copy scans
  - absence outcome letters
  - rendered Evidence PDFs for both populations
- **Why it matters:** a carer, a Viewer, On Call or a Senior can list and download HR and care records through the Storage API with their own login. The app never offers this, but the database allows it.
- **Likely fix:** the app already signs downloads on the server.
  - Drop the select policy, so only the service role reads the bucket.
  - Or make it mirror the Evidence and Evidence file rules by matching the path to the row.
  - Then re-run the carer probe and expect 0.

### S4. Medium: support mode can still write

- **Where:**
  - `lib/people/actions.ts:1659` `completeCheck`
  - `lib/service-users/actions.ts:819` `completeCheck`
  - `lib/people/actions.ts:1480` `completeTrackerForm`
  - These call `requireCompany()` and never check `actingAsCompanyId`.
  - The refusal (DEF-006) is only on the page: `app/(app)/people/[id]/checks/[instanceId]/complete/page.tsx:52`.
- **What does refuse support mode:**
  - Updates, own rating, paper upload and SAR.
  - Everything else accepts a write, because `applyManageAs` (`lib/auth/guards.ts:62`) acts as `company_admin`.
- **Mitigation already there:** these writes are audit tagged `impersonating: true`.
- **Likely fix:** a decision first, either look only or full support. Then one central `requireCompanyWrite()` guard. At minimum, put the DEF-006 check in those three actions.

### S5. Medium: calendar feeds outlive the login

**Status, 3 Oct 2026: BUILT (migration 0380, deploy pending).** A feed is served only while its login is active, in that company, and the company is live (feedOwnerIsLive, 5 unit tests). A trigger deletes the feed the moment the login is disabled, closed by leaving, or moved company.

- **Where:** `lib/planner/calendar-feed.ts:193` `loadFeedByToken`. It uses the service client and never checks `profiles.status` or the company's status. Feeds are only removed by their owner.
- **Data:** no disabled login has a feed today, so this is a risk, not a live leak.
- **Why it matters:** a leaver's Outlook would keep pulling visits with Service User names.
- **Likely fix:** return nothing unless the profile is active and the company is live. Delete feeds when a login is disabled or the person leaves.

### S6. Medium: single session is enforced in the website only

- **Where:**
  - `requireUser` (`lib/auth/guards.ts:110-160`) signs out a displaced session when it next visits a page.
  - `claim_session` (0273) only records the slot.
  - No RLS rule looks at the session.
- **Why it matters:** a displaced device's access token still works directly against the Supabase API, Realtime and Storage until it expires (about an hour), and its refresh token is not revoked. Device kind also comes from the browser's User-Agent, which can be faked (documented in 0273).
- **Likely fix:** in `claim_session`, delete the displaced session from `auth.sessions` so its refresh token dies. Optionally add a current session check to the core helpers.

### S7. Medium: some Service User reads are not audit logged

- **Audited:**
  - opening the Service User record (`service_user.viewed`)

- **Not audited:**

  - `service-users/[id]/care-plan`, `care-schedule` and `outcomes` pages
- **Likely fix:** write `evidence.viewed` and `service_user.<page>_viewed` audit rows on those pages.

### S8. Low: `seed_requirement_map` has no permission check

- **Where:** SECURITY DEFINER, executable by `anon` and `authenticated`, no caller check.
- **Effect:** anyone can call `/rest/v1/rpc/seed_requirement_map` with a company id. It re-adds the default Readiness mappings, which would undo a mapping a company removed. It never deletes or reads.
- **Likely fix:** revoke EXECUTE from `anon` and `authenticated`. The trigger that calls it runs as owner anyway.

### S9. Low: AI import from a link, private address guard

- **Where:** `lib/form-builder/ai-import.ts:138-158` blocks private addresses by text only.
- **Gaps:** a public host name that resolves to a private address passes, and so do mapped IPv6 and 100.64/10.
- **Limits:** Company Admin and Founder only. Redirects are re-checked.
- **Likely fix:** resolve the host and check every address before fetching.

### S10. Low: Evidence attachments

- **Where:**
  - `lib/people/actions.ts:1506` takes any file with the browser's own type.
  - `lib/evidence/submit.ts:120` uploads before `submit_evidence` authorises the save, so a refused save leaves orphan files.
  - The `evidence` bucket has no size limit or type list. The company logo has the same gap.
- **Likely fix:** an allow list of types plus a size cap. Upload after the RPC succeeds, or clean up on refusal.

### S11. Low: whistleblowing raiser in the audit log

- **Where:** `lib/whistleblowing/raise.ts:57-61` writes the named raiser's id and email to `audit_log`, which the Founder can read. The content stays private.
- **Likely fix:** leave the actor out for this action, or hide `whistleblowing.*` rows from the Founder's audit views.

### S12. Low: users can edit their own email and custom role

- **Where:** the trigger guards only role, company and status.
  - A user can change `profiles.email` on their own row.
  - They can also switch to another custom role with the same built in role, which only changes what menus show.
- **Likely fix:** guard `email` (it should follow the login) and `company_role_id` (Admin only).

### S13. Low: a deleted company's logins keep database access during the grace period

- **Data:** House Test Ltd was deleted at 01:06 today and its Admin profile is still active.

### S14. Low: form drafts skip the single session check

## Bugs

### B1. Medium: the dashboard refresh storm (feeds the "site is slow" complaint)

**Status, 3 Oct 2026: FIXED.** Debounced refresh (one per 3 seconds at most), poll only when the live connection is down, rejoin when the tab comes back, company row read once per request. Idle requests went from 800 to 3,500 a minute to 0. The background tab rejoin passed in Chrome: silent while hidden, one refresh on return.

- **Where:** `components/realtime-refresh.tsx`, mounted on the dashboard.
  - Every live change to people, checks or trackers calls `router.refresh()` straight away, with no debounce.
  - A 10 second poll also runs while the tab is visible, even when the live connection is healthy.
  - Each refresh re-renders the whole dashboard. One render reads the same `companies` row about nine separate times with different columns, plus readiness 1 + N.
- **Proof, Supabase API logs, 2 Oct 10:00 to 10:30 UTC:**
  - Thistle's Admin login made 54,386 requests.
  - The old demo login made 43,018.
  - Each dashboard re-rendered about every 3 seconds (19 identical `companies` reads per minute per login).
  - Traffic dropped from about 26,000 to about 200 per 5 minutes the moment it stopped, just before the Demo company was recreated at 10:41.
  - 24 hour total: 265,000 API requests for a handful of users.
- **Likely fix:**
  - Debounce refreshes (for example one per 2 to 3 seconds, trailing).
  - Poll only when the socket is down.
  - Read the company row once per request with React `cache()`.
  - Do this alongside the agreed RLS speed pass.

### B2. Medium: Supervisors lose the login box on a Person record

**Status, 3 Oct 2026: FIXED (migration 0379, Phil chose "Allow, own branch").** person_login_status now asks is_branch_lead, the same question as the invite (0316). Proved in a rolled back probe: a Thistle Supervisor was refused before and sees the status after; another company stays refused. The page now logs a refusal instead of hiding it.

- **Where:**
  - `app/(app)/people/[id]/page.tsx:212` calls `getPersonLoginStatus` when `canManage`, which includes Supervisors and Recruiters.
  - The RPC `person_login_status` allows only company wide roles and Branch Managers, and raises "You do not have permission".
  - `lib/staff/data.ts:129` swallows the error and returns null.
- **Proof:** 16 HTTP 400 responses in 24 hours, all from Thistle's two Supervisors (`dd1b8fe3…`, `34b77278…`).
- **Likely fix:** make the page gate and the RPC agree (a decision: should Supervisors and Recruiters see and send logins? 0316 suggests the person who adds a carer can). Log the error instead of hiding it.

### B3. Low: UTC "today" in Readiness

- **Where:** `get_framework_check_readiness` uses `current_date`, and the database runs in UTC. `check_rag` (registers, dashboard) uses `Europe/London`. `expire_evidence_retention` and `expire_record_update_retention` also use `current_date`.
- **Effect:** between 00:00 and 01:00 in summer, Readiness and the registers disagree on what is overdue.
- **Likely fix:** use `(now() at time zone 'Europe/London')::date`.

### B4. Low: Readiness and the registers count different people

- **Where:**
  - Readiness (RPC and `getFrameworkItems`) counts only `employment_status = 'active'` and Service Users `active`.
  - `person_check_status` includes `mat_leave`.
- **Data:** Seren Owens (Demo, maternity leave) shows 10 checks on the register and none in Readiness. A Service User in hospital is the same.
- **Likely fix:** a decision on one rule, then apply it in both places.
